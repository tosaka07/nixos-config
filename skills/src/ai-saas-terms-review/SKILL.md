# AI/SaaS Terms Review

## Purpose

企業でAI/SaaSを利用する前に、公開規約・プライバシーポリシー・Usage Policy・DPA・SLA・セキュリティ資料を読み、リスクと追加確認事項を日本語で整理する。

このスキルでは、条項を過度に危険視せず、次の2つを分ける。

1. SaaS一般条項として通常確認に留めるもの
2. AI/LLMサービス特有または企業導入上の重点リスクとして残すもの

## Default workflow

1. 対象文書を特定する
   - Terms of Service
   - Privacy Policy
   - Usage Policy / Acceptable Use Policy
   - DPA / Data Processing Addendum
   - SLA
   - Security / Trust Center
   - Subprocessor list
   - Pricing / Enterprise FAQ
2. 各文書のURL、文書名、Effective date / Last updated、確認日を記録する。
3. サービス構造を把握する。
   - 単体SaaSか、外部LLM連携か、AIオーケストレーションか、RAG/エージェント型か
   - 入力・出力・アップロードファイル・ログ・メタデータがどこを通るか
4. `references/checklist.md` の観点で調査する。
5. `references/report-format.md` の形式で日本語レポートを作成する。
6. 不明点は「確認不可」「要問い合わせ」と明記し、推測で断定しない。
7. 最後に、導入前にベンダーへ問い合わせるべき質問を優先度順にまとめる。

## Risk classification

各論点は次のいずれかに分類する。

| 判定             | 意味                                                                 |
| ---------------- | -------------------------------------------------------------------- |
| 問題なし         | 通常のSaaS条項で、現時点で特段の追加対応は不要                       |
| SaaS一般・要確認 | 一般的な条項だが、企業導入では証跡や詳細確認が必要                   |
| AI固有・重点確認 | 学習利用、外部LLM、モデルルーティングなどAIサービス特有の確認事項    |
| 重点リスク       | 機密情報・個人情報・規制業務で利用制限や契約交渉が必要な可能性が高い |
| 確認不可         | 公開文書では判断できないため、ベンダー確認が必要                     |

## Priority rules

高優先度として扱う項目:

- 入力・出力・アップロードファイル・ログが学習、評価、品質改善、ファインチューニングに使われるか
- 学習利用のデフォルト設定とオプトアウト可否
- オプトアウトが外部LLMプロバイダー側にも適用されるか
- 外部LLM、サブプロセッサ、クラウド、分析、監視、サポート、決済などの送信先
- データ処理国、保存国、バックアップ保存国、サポート閲覧国
- DPA締結可否とDPA内の再委託、国外移転、削除、監査、事故通知、非学習条件
- データ保持期間、削除範囲、外部ベンダーキャッシュ、バックアップ、監査ログ、学習済みモデルの扱い
- SOC 2 Type II、ISO27001、ISMAPなど第三者認証または監査報告書
- Usage Policy上、想定用途が禁止・制限されていないか

## Interpretation rules

- 国外転送があること自体を直ちに重大リスクとしない。処理国・保存国・移転根拠・国内固定可否の確認論点として整理する。
- アカウント情報、請求情報、技術ログ、サポート情報の取得は通常のSaaS条項として扱う。ただし保持期間、削除、再委託、国外移転は確認する。
- サービス提供、保守、セキュリティ、不正防止、法令遵守目的の処理は一般的なSaaS運用として扱う。ただし目的外利用や学習利用と混同しない。
- 「学習利用」「改善利用」「評価」「分析」「品質向上」「ファインチューニング」は別々に確認する。学習ではない改善利用にも注意する。
- 「外部LLMとしてA/B/Cを利用することがある」という記載が例示か限定列挙かを確認する。限定と明記されていない場合は未記載ベンダーの可能性を残す。
- 削除可能と書かれていても、バックアップ、監査ログ、法令保存、外部ベンダーキャッシュ、学習済みモデル、派生データが例外にならないか確認する。
- Outputの権利帰属がユーザーにある場合は肯定材料として扱う。ただしサービス側への広範なライセンス、再許諾、マーケティング利用は別途確認する。
- 出力保証なし、責任制限、補償義務はSaaS/AIで一般的。ただし高リスク用途では人間レビューと社内責任分界を提案する。

## Output standards

- 日本語で書く。
- 最初に3〜8行のtl;drを置く。
- 「公開文書上確認できること」と「追加確認が必要なこと」を分ける。
- 重要な論点は表で整理する。
- ベンダーに問い合わせるべき質問は、最優先、次点、用途次第に分ける。
- 不明な情報は「不明」「公開文書上は確認不可」と書く。
- 法的助言として断定せず、企業導入審査・契約確認のための整理として書く。
- 口語ではなく、文語を使用する。
- `japanese-tech-writing` スキルを使用し、文書を作成する
